# 种草流水线 · 品牌内容 Copilot

> 一条 brief 进来，出 3 篇可交付的小红书种草稿。
> 每篇都能回答三个问题：**这句话的依据在哪、有没有越界、成本多少。**

一个可运行的 demo（本地 30 秒起）：`python3 server.py` → http://localhost:8017

---

## 1. 为什么做这个

针对的是**内容营销公司**的 AI 落地场景，不是通用文案工具。

这类公司（小红书生态服务商、MCN、4A 转型的数字营销团队）现在的处境很具体：

- **个人提效已经发生，组织提效没发生。** 策划自己用 AI 写得飞快，但团队里换个人接手同一个客户，还是得从头讲一遍品牌调性、卖点边界、哪句话不能说。
- **已有 AI 系统，但停在"生成"这一层。** 大多数团队的 AI 内容系统做的是"给关键词 → 出稿"，产出无法向客户解释、无法追责。
- **真正的成本不在写，在改和担责。** 一篇稿子从初稿到过客户和平台审核，改稿占大头；一旦出现"修复""7天见效""全网最"这类表述，删稿、限流的代价由服务商承担。
- **平台已经能识别模板化批量内容。** 同一批账号发句式高度相似的稿子会被判营销号。所以"生成更快"在种草地盘上是**负资产**——快出来的东西长得一样。

结论：这类公司缺的不是产能，是**把资深策划的判断力变成可复用、可追溯、可度量的流程**。AI 在这条链路上的位置不是"写手"，是**产线**。

## 2. 产品结构：三层

```
┌─ 资产层 ────────────────────────────────────────┐
│ 品牌 voice / 卖点卡（带证据等级）/ 人群洞察      │
│ 爆文骨架 / 竞品卡 / 平台规则                     │
│ 关键：只有「有证据」的卖点能作为主张被引用        │
└──────────────────────────────────────────────────┘
                    ↓ 检索（BM25 + 客户指定卖点锚点）
┌─ 生产层 ────────────────────────────────────────┐
│ ① Brief 解析  ② 资产召回  ③ 策略（三种骨架）     │
│ ④ 并行撰写    ⑤ 合规闸门 + 事实核对  ⑥ 度量      │
└──────────────────────────────────────────────────┘
                    ↓
┌─ 交付层 ────────────────────────────────────────┐
│ 可溯源（每个卖点对应哪条资产）                    │
│ 可拦截（违规词 + 无据数字）                       │
│ 可度量（一次通过率 / 改写率 / 覆盖率 / 成本）      │
│ 人工位（合并前必审，不设自动发布）                 │
└──────────────────────────────────────────────────┘
```

## 3. 四个关键设计判断

### 3.1 合规闸门用规则，模型只负责改写

违禁词表是**确定**的。让模型做合规检查，它会给出一段听起来专业的判断，但会漏、会解释、会改口——而漏一个就是一个投放事故。规则引擎还能给出**精确位置**，策划才能一处一处改；模型只能说"这句有问题"，落不了地。

分工因此是：**规则负责发现，模型负责改写，人负责过审。**

配套的一个细节：规则要能排除误报。`第一次用`、`湿度 31%` 这类正常表达如果被拦，策划三次之后就再也不看这个面板了——**一个会被无视的检查，比没有检查更危险**。所以规则里维护了「序数词排除」「百分比仅在功效语境下才算宣称」这类上下文判断。

### 3.2 检索用 BM25 + 锚点，不上向量库（现阶段）

- 品牌资产是几十到几百条的量级，稀疏检索的召回在这个规模上不输向量检索；
- 命中项和命中词能直接给人看，策划能判断"它为什么召回了这条"——这是内容团队愿意信任系统的前提；
- 零额外依赖、零额外延迟、零 embedding 成本。

但纯 BM25 有一个真实缺陷，我在开发中撞到了：**它对业务约束无感**。客户说"这次主推三油配方"，BM25 只按相似度排，可能召回了一堆痛点洞察却漏掉主卖点。所以加了一层**锚点召回**：客户点名的卖点先落位，再叠相似度召回。生产环境会升级成 hybrid（BM25 + embedding），但 BM25 应作为召回基线保留——用来兜住"向量检索偶尔漏掉明确关键词"的情况。

### 3.3 要有对照组

没有对照组，任何系统都可以说自己的产出更好。所以每次运行都同时跑一条**裸生成**路径（不给品牌资产、不给调性、不过闸门），用同一套指标打分。

需要诚实地加一句：**对照组不是永远更差。** 在 brief 写得很清楚的正常场景里，裸生成也能出 4/5 卖点覆盖、0 违规——这是模型的进步，不该被掩盖。差距是在下面两种情况拉开的：

- 客户硬塞了不合规说法（`能修复皮肤屏障`、`七天见效`、`全网最温和`）→ 裸生成原样写进去，闸门拦下 5 处后改写为 0；
- 需要 3 篇不重样的稿子 → 裸生成出一篇，模板化风险最高。

这个结论比"全面碾压"更有用：它告诉业务方**什么场景值得上系统、什么场景自己写就行**。

### 3.4 不追求一次生成到位

链路是「生成 → 拦截 → 改写 → 复核」，不是「一次写对」。第一遍允许越界，因为写手（模型）的职责是写得好、按客户要求交付，**合规不是写手的职责**。这也符合真实分工：文案不管法务。

改写只动有问题的句子，不重写整篇——否则"合规"会变成"把人的东西磨平"，那正是策划最反感 AI 的地方。改写稿允许承认局限（"用久了还是会干"），这比硬转话术更可信。

## 4. 指标定义

| 指标 | 定义 | 为什么看它 |
|---|---|---|
| 合规一次通过率 | 初稿未命中任何违规项的比例 | 衡量提示词与资产对写手的约束力 |
| 违规拦截数 / 终稿违规数 | 闸门拦下多少、改写后剩多少 | 衡量闸门有效性，终稿必须为 0 |
| 无据事实数 | 数字类主张在品牌资产中找不到依据 | 比违禁词更贵：编造价格/检测会引来投诉 |
| 卖点覆盖率 | 命中卖点数 / 库内卖点总数 | 客户最关心的一条，也最容易被模型漏 |
| 平均字数 / 段数 | 结构完整性 | 小红书正文节奏，段落过长的稿子完读率低 |
| 端到端耗时 | 一次运行 wall time | 决定策划是否愿意用 |
| 模型调用次数 | 每轮成本口径 | 直接换算成 token 成本 |

实测（本机，deepseek-flash）：
- 3 篇 + 1 篇对照，端到端 **≈ 49 秒**，**8 次**模型调用；
- 正常 brief：合规一次通过 **3/3**，卖点覆盖 **4/5**，无据事实 **0**；
- 客户违规要求场景：初稿违规 **5 处**（最好 / 全网最 / 最温和 / 修复 / 三天）→ 改写后 **0**。

## 5. 边界（写在明处）

1. **真人细节必须真人给。** 模型会写出"我儿子跟我一起洗澡"这种细节，听起来真实，但它不是真的。生产环境需要策划填 1-2 条真实体验，AI 负责长成一篇完整的稿子，而不是替人编生活。
2. **爆文骨架依赖真实数据。** demo 里的三种骨架是行业通用结构。真正有价值的是客户自己的历史爆文拆解（哪类开头收藏率高、哪类结构转发率高），这需要历史内容 + 数据回流。
3. **事实核对目前只覆盖数字。** 成分、检测机构、资质类主张还没有结构化，需要接入品牌方的事实库。
4. **合规规则是大陆法规 + 小红书规则。** 投抖音/知乎需要换规则集，但闸门框架不变。
5. **没有做投放后归因。** 内容是前端，真正闭环要靠曝光/收藏/转化的回流数据——那是下一阶段。

## 6. 如果继续做（3 个月路线）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| 第 1 月 | 接 1 个真实客户资产，替换 demo 资产库；补真人细节填充分支 | 策划愿意连续用 2 周 |
| 第 2 月 | 历史爆文反解析：从客户过去的爆文里自动抽骨架 + 建评测集（20 条） | 人工改写率下降 30% |
| 第 3 月 | 多平台适配 + 投放数据回流，把"哪类结构转化好"接回策略层 | 形成可复用的骨架优选逻辑 |

度量口径固定不变：**人工改写率、合规一次通过率、单篇成本**。这三条不改善，功能加得再多也是假的。

## 7. 技术实现

- Python 标准库 + 一个 LLM API，**零第三方依赖**，`python3 server.py` 即起；
- 前端单文件（无构建），SSE 推送每一步进度；
- 检索：手写 BM25（中文 char-bigram）+ 锚点召回；
- 闸门：正则规则引擎（7 类规则、70+ 词条）+ 数字白名单事实核对；
- 约 700 行代码，全部可读：`engine/{retriever,audit,factcheck,pipeline,llm}.py`

**为什么选这么朴素的栈**：这个 demo 要在自己电脑、面试现场、客户机房三种环境都能跑起来。少一个依赖就少一次现场翻车。
